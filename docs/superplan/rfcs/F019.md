# 功能开发中的可选 RFC 阶段

## 摘要

在现有 feature 生命周期中增加一个可选、需要人类审批的 RFC 阶段。Feature 仍是唯一的需求和完成状态载体；当人类明确要求，或 AI 识别到会实质影响设计的风险时，在生成开发计划前创建 RFC 并完成评审。

RFC 默认使用中文。只有当人类明确指定其他语言，或项目已有不同的文档语言规范时，才使用对应语言。

## 背景

Superplan 当前会将已接受的 feature 直接转换为 draft 开发计划。对于边界明确的工作，这已经足够；但复杂变更可能需要先确定架构、契约、迁移或风险处理方式，否则文件级任务和验证方案容易建立在尚未确认的假设上。

如果把 RFC 设计成另一种需求类型，会与 feature 在需求归属、编号、路由和完成状态上重复。如果把 RFC 放入 `docs/superplan/plans/**`，则会把设计文档和可执行计划混在一起。

F019 本身会改变公开工作流、审批门禁、解析和校验契约，因此作为新流程的自举案例使用 RFC。本文档获得批准前，不得创建 F019 的开发计划。

## 目标

- 保持 `feature` 是唯一的人类需求、来源编号和完成生命周期。
- 支持人类显式要求 RFC，也允许 AI 在存在实质设计风险时自主选择 RFC。
- AI 自主选择 RFC 时必须公开具体判断依据。
- RFC 获得人类批准后，才能创建开发计划。
- RFC 文档与可执行计划分离，同时继续使用 feature id 保持追踪关系。
- RFC 默认使用中文，并允许人类或项目规范显式覆盖。
- 提供一份精简的 RFC 编写规范和修订留痕规则。
- 保持当前四个顶层 skill 和条件引用架构。
- 通过仓库工具和行为测试强制执行跨产物状态规则。

## 非目标

- 不新增 `docs/superplan/human/rfcs.md`。
- 不新增 `R` 编号、RFC plan type 或顶层 RFC skill。
- 不要求所有 feature 使用 RFC，也不因任务规模大就自动使用 RFC。
- 不开发自动生成开发计划的工具。
- 不把 RFC 扩展为通用 ADR、项目提案或文档管理系统。
- 不建立翻译或多语言同步系统。
- 不默认保存逐轮对话、评审聊天或措辞修改日志。
- 不改变现有 feature 状态流和开发计划状态流。
- 不迁移已完成的历史 feature、计划或设计资料。

## 决策

### 1. Feature 条目选择是否启用 RFC 流程

Feature 条目可以包含一个结构化字段：

```markdown
- requires_rfc: true
```

该字段可选；缺失时按 `false` 处理，以保持向后兼容。请求解析器需要校验该字段最多出现一次，并且值只能是 `true` 或 `false`。请求工具必须能够在记录 feature 时事务性地写入该值；将已有的 accepted feature 调整为需要 RFC 时，也必须使用安全的规范化修改边界，不能通过人工改编号或大范围覆盖文件完成。

RFC 决策必须在创建开发计划之前完成：

- 人类明确要求 RFC 时，记录 `requires_rfc: true`。
- 人类没有说明时，由 AI 根据下述标准判断。AI 决定使用 RFC 时，必须先说明具体原因，再创建 RFC 并持久化 `requires_rfc: true`。
- 人类明确拒绝 RFC 时，使用直接 feature 流程；如果 AI 发现重大风险，应说明风险并重新请求确认，不能静默覆盖人类决定。
- 一旦存在非 `superseded` 的开发计划，请求工具必须拒绝静默修改 RFC 要求。之后若需改变流程，必须取得人类明确批准并执行结构性计划评审。

### 2. AI 自主判断基于实质设计风险

当下列任一情况可能实质改变开发计划或验收结果时，适合使用 RFC：

- 存在多个具有重要取舍的可行架构；
- 跨模块归属或共享基础设施边界不明确；
- 公共契约、兼容性承诺、数据模型或迁移方式发生变化；
- 安全、隐私、并发或数据完整性行为需要明确决策；
- 必须设计发布、回滚或运行故障处理方式；
- 产品或领域边界存在实质歧义，直接写开发计划会依赖未经确认的假设。

代码量、任务数量、AI 对代码不熟悉，或单纯希望增加文档，都不能单独构成启用 RFC 的理由。

### 3. RFC 是 feature 所属的设计文档

规范路径为：

```text
docs/superplan/rfcs/<feature-id>.md
```

文件名使用完整且大小写一致的 feature id；在 worktree 中产生的分支限定编号也必须原样保留，例如 `F019@feature-x.md`。RFC frontmatter 包含 `id`、`title`、`status`、`version`、`source` 和 `created`。

RFC 状态只保留：

```text
draft -> approved
```

离开 `draft` 必须取得人类批准。对 approved RFC 进行实质修改时，必须先将其恢复为 `draft`，递增版本号，修改后的内容重新获得批准才可继续作为权威设计。Git 历史负责记录具体修订；F019 不引入 RFC 文件版本编号或 superseded 文档图。

RFC 正文必须包含问题、目标、非目标、决策、重要替代方案、生命周期与兼容性影响、风险以及可观察的批准条件。RFC 应解决会影响开发计划的关键决策，但不能包含逐文件开发任务。

### 4. RFC 默认使用中文

RFC 的标题、说明、决策、风险和批准条件默认使用中文。代码标识符、命令、文件路径、frontmatter 字段和不宜翻译的标准术语保持原样。

以下情况可以覆盖默认语言：

- 人类明确要求使用其他语言；
- 仓库或项目规范明确要求使用其他文档语言；
- RFC 面向的外部协作方有已确认的语言要求。

语言选择只影响 RFC 文档表达，不改变状态、审批、编号或校验规则。该规则不要求自动翻译历史 RFC。

### 5. RFC 编写规范保持精简

规范由 `skills/feature-plan-and-delivery/references/rfc-spec.md` 统一维护，并且只包含会影响 RFC 产物和审批的规则。

RFC 必须包含以下 frontmatter：

- `id`：与 feature id 完全一致；
- `title`：清晰描述设计主题；
- `status`：`draft` 或 `approved`；
- `version`：从 `1` 开始的正整数，表示已批准设计版本；
- `source`：`docs/superplan/human/features.md`；
- `created`：稳定的 `YYYY-MM-DD` 日期。

RFC 正文至少包含：

- 摘要；
- 背景或问题；
- 目标；
- 非目标；
- 决策；
- 已考虑的重要替代方案；
- 风险与缓解措施；
- 可观察的批准条件。

兼容性、迁移、发布、回滚、安全或数据影响仅在相关时增加。RFC 记录会影响开发计划的设计边界，不嵌入逐文件任务、实现代码、聊天记录或机械步骤。

### 6. Git 是默认修订历史

RFC 在 `draft` 阶段直接维护当前最佳版本，不要求记录每轮对话或每次措辞调整。最终文档应保留当前决策，以及对理解决策有价值的被否决方案和理由，而不是按时间复述讨论过程。

版本号表示设计审批版本，而不是编辑次数或对话轮次：

- 新 RFC 从 `version: 1` 开始；
- 首次批准前的 draft 修改不递增版本；
- approved RFC 发生实质修改时，先恢复为 `draft`，再将版本递增一次并重新审批；
- 文字修正、排版调整等不改变设计含义的修改不递增版本；
- 版本号必须连续递增，不能回退或复用。

修改留痕规则为：

- 普通 draft 修改直接更新正文，不增加修订表；
- 重要设计取舍写入“已考虑的替代方案”；
- Git diff 和提交历史是默认的权威修订记录；
- approved RFC 发生实质修改时，必须先恢复为 `draft`，修改后重新审批；
- 只有人类、项目规范、审计或合规要求明确提出时，才增加简短的“修订记录”，并且只记录已批准版本的日期和决策摘要。

不得把完整聊天记录、逐轮评审意见、checkpoint 或实现进度复制到 RFC 中。

### 7. 开发计划仍是普通 feature 计划

RFC 对应的开发计划仍放在：

```text
docs/superplan/plans/features/<feature-id>/
```

计划继续使用 `type: feature`、现有 `Fxxx[-NN]` 编号，并以 `docs/superplan/human/features.md` 作为 source。每个 RFC feature 的开发计划必须在 `References` 中列出准确的 RFC 路径。

对于 `requires_rfc: true` 的 feature，如果对应 RFC 不存在、校验失败或状态不是 `approved`，全局计划校验必须拒绝任何非 `superseded` 的开发计划。RFC 批准只授权创建开发计划，不授权代码开发；开发计划仍需独立审批。

### 8. Feature 完成生命周期保持不变

Feature 在 RFC 评审、计划评审和代码开发期间保持 `accepted`。现有 `accepted -> done` 规则继续要求至少存在一个非 `superseded` 的相关计划，并且所有相关计划均为 `complete`。对于 RFC feature，完成时还必须确认对应 RFC 仍然有效且为 `approved`。

完整流程为：

```text
feature proposed
  -> feature accepted
  -> RFC draft
  -> RFC approved
  -> implementation plan draft
  -> implementation plan approved/in_progress
  -> implementation plan complete
  -> feature done
```

### 9. 现有 feature skill 负责条件行为

新增精简条件引用 `skills/feature-plan-and-delivery/references/rfc-spec.md`。只有当人类明确要求 RFC，或请求被标记为 `requires_rfc: true` 时，feature skill 才加载该引用。

该引用负责 RFC 选择标准、默认语言、文档结构、审批和开发计划门禁；共享 delivery 和 plan reference 继续承担现有跨路由规则。不得新增第五个顶层 skill，入口路由仍将请求识别为 feature。

### 10. 校验和发现保持适度

现有 human 和 plan 命令继续作为主要状态发现接口：

- Human summary、list 和 show 应能展示活动 feature 是否需要 RFC，但不输出 RFC 正文。
- 精确 feature 查询保留结构化字段。
- RFC 评审只读取当前 feature 对应的 RFC 文档。
- Plan catalog 和 search 继续只处理可执行计划；RFC 保持在 `plans/**` 外。
- 全局计划校验只加载证明跨产物状态所需的准确 RFC 文档。

首个版本不增加独立 RFC catalog、通用搜索或自动翻译命令。

## 兼容性与迁移

- 缺少 `requires_rfc` 的现有 feature 按 `false` 处理。
- 现有计划保持有效，无需重写。
- `docs/superplan/rfcs/` 在首次创建 RFC 时按需生成；初始化不需要创建或强制保留空目录。
- 新工作区的 feature 指引可以说明可选字段和中文默认规则，但 workspace migration 不重写已有的用户维护 human 文件。
- 可选字段和按需目录属于增量兼容变更；除非实现阶段发现不可兼容的生成产物变化，否则不提升 workspace schema。

## 已考虑的替代方案

### 独立 RFC 请求注册表

拒绝。`rfcs.md`、`Rxxx` 编号和单独的 RFC 完成生命周期会与 feature 重复，并导致交付状态归属不清。

### 独立顶层 RFC skill

拒绝。RFC 是 feature 的条件阶段。第五个可发现路由会增加触发歧义，并违背现有条件引用架构。

### 将 RFC 放入 `plans/rfcs/`

拒绝。`docs/superplan/plans/**` 下除索引外的 Markdown 都属于可执行计划，需要遵守计划 frontmatter、依赖、状态和索引规则。

### 为每个 feature 创建 RFC 子目录

拒绝首版采用 `docs/superplan/rfcs/<feature-id>/rfc.md`。当前契约是一项 feature 最多对应一个 RFC，使用 `docs/superplan/rfcs/<feature-id>.md` 映射更直接，读取、引用和校验更简单；附件和多文档 RFC 体系属于非目标。

### 将设计直接写入开发计划

拒绝。对于需要 RFC 的工作，这会把设计选择和可执行交付评审合并为一个审批门，无法满足两阶段对齐要求。

### 根据提问语言自动选择 RFC 语言

拒绝作为默认规则。短提示、代码或英文术语不应导致整个 RFC 改用其他语言；中文是稳定默认值，只有明确的人类或项目要求才覆盖。

## 风险与缓解措施

- **流程膨胀：** AI 可能过度选择 RFC。通过实质风险标准和禁止仅按规模判断来约束。
- **静默增加流程：** AI 可能在不说明的情况下增加审批步骤。要求其在持久化 RFC 要求前说明具体原因。
- **状态漂移：** RFC 未批准时可能产生开发计划，或 approved RFC 被实质修改。通过全局校验以及实质修改必须回到 `draft` 的规则约束。
- **语言不一致：** 不同代理可能根据提示语言生成不同语言的 RFC。通过中文默认值和明确覆盖条件保持一致。
- **过程日志膨胀：** 多轮对话可能被完整写入 RFC，降低当前决策的可读性。默认只维护当前设计和重要替代方案，并由 Git 保存修订历史。
- **版本含义漂移：** 不同代理可能按编辑次数递增版本。将版本严格定义为已批准设计版本，并要求正整数连续递增。
- **说明重复：** RFC 规则可能散落在多个 skill 和 reference。通过一个 feature route 条件引用，以及共享规范中最少量的跨产物条款控制。
- **兼容性回归：** 历史 feature 可能被视为缺少必填字段。缺失值按 `false` 处理，并使用历史 fixture 覆盖。

## 批准条件

当人类同意以下内容时，本 RFC 可以获批：

- RFC 是 feature 的可选阶段，不是独立需求类型。
- 人类显式选择和 AI 基于证据的自主判断都可以启用 RFC。
- AI 自主选择 RFC 时必须说明原因。
- RFC 默认使用中文，除非人类或项目规范明确覆盖。
- RFC 遵循精简的必需章节规范，不包含逐轮聊天或实现任务。
- Git 是默认修订历史；approved RFC 的实质修改必须回到 `draft` 并重新审批。
- RFC 包含正整数版本号；新文档从版本 1 开始，只有 approved 设计发生实质变更时才递增。
- RFC 位于 `plans/**` 之外，并使用 feature id。
- RFC 批准后才能创建开发计划，开发计划批准后才能编码。
- 现有 feature、计划、skill 清单和 workspace 兼容契约保持不变；如果实现验证发现必须调整，需要另行评审。
