# 一个 Feature 支持多个 RFC

## 摘要

扩展现有可选 RFC 阶段，使一个 feature 在存在多个独立设计审批边界时可以拥有多个 RFC，同时保持单 RFC 的平铺路径完全兼容。单 RFC 继续使用 `docs/superplan/rfcs/<feature-id>.md`；多 RFC 使用 `docs/superplan/rfcs/<feature-id>/NN-<slug>.md`。同一 feature 只能选择其中一种布局。

多 RFC 模式中的每份文档拥有独立 RFC id、状态和版本，但仍显式归属于同一个 feature。所有匹配 RFC 都批准后才能创建开发计划；每个开发计划只引用自己的直接 RFC 输入，并且至少引用一份匹配 RFC。

## 背景

Superplan 0.6.0 将 RFC 定义为 feature 的可选设计阶段，并采用 `docs/superplan/rfcs/<feature-id>.md` 的一对一路径。该模型读取、引用和校验简单，适合一项 feature 只需要一次整体设计审批的情况。

实际 feature 可能包含多个可以独立评审的设计主题，例如存储模型与发布策略。将它们强制合并到同一 RFC 会使审批、版本变化和计划引用过度耦合；将 feature 拆成多个请求又可能破坏其统一的用户价值和完成生命周期。因此需要在不引入独立 RFC 请求类型的前提下支持一对多设计文档。

当前实现存在以下一对一假设：

- RFC 发现器明确拒绝 `rfcs/` 下的嵌套 Markdown；
- RFC `id` 必须与 feature id 和平铺文件名完全相同；
- 全局校验器以 feature id 映射单个 RFC；
- 每个 RFC-backed plan 必须引用唯一的平铺 RFC 路径；
- skill、workspace 指引、README 和行为测试都描述单 RFC 契约。

## 目标

- 保持现有单 RFC 路径和元数据有效，不要求迁移历史文档。
- 允许一个 feature 使用目录保存一份或多份独立 RFC。
- 为多 RFC 提供稳定、不会与 split plan id 混淆的 RFC 身份。
- 对单 RFC 和多 RFC 使用确定且互斥的路径规则。
- 保持 RFC 是 feature 的条件设计阶段，不新增请求类型、plan type 或顶层 skill。
- 在创建开发计划和完成 feature 时强制所有匹配 RFC 已批准。
- 让每个开发计划只引用直接影响它的 RFC，同时保证至少存在一个匹配引用。
- 支持 branch-qualified feature id，并保持全局校验、完成边界和原子状态修改正确。

## 非目标

- 不要求普通 feature 或所有复杂 feature 使用 RFC。
- 不把 RFC 变成通用 ADR、附件目录、知识库或独立索引系统。
- 不允许同一 feature 同时使用平铺文件和目录布局。
- 不引入 RFC 之间的依赖图、部分实施状态或独立完成生命周期。
- 不允许在部分 RFC 尚未批准时开始同一 feature 的开发计划。
- 不自动拆分现有 RFC，也不自动迁移历史路径。
- 不在本 feature 中发布新插件版本、推送远端或刷新本地安装。

## 决策

### 1. 保留平铺单 RFC 作为默认布局

只需要一个整体设计审批时继续使用：

```text
docs/superplan/rfcs/F123.md
```

其 frontmatter 保持现有契约：`id` 与 feature id 完全一致，不增加 `feature` 字段。现有平铺 RFC 在新实现中不需要任何修改。

RFC 篇幅较长、包含多个章节或对应多个开发计划，本身不构成使用多 RFC 的理由。只有设计主题需要独立审批、独立版本变化或独立计划引用时才使用目录布局。

### 2. 多 RFC 使用 feature 目录和带语义的有序文件名

多 RFC 布局为：

```text
docs/superplan/rfcs/F123/
├── 01-storage-model.md
└── 02-rollout-strategy.md
```

目录名必须与完整 feature id 一致，包括 branch-qualified id。文件名使用两位正整数序号、短横线和小写 kebab-case 语义名称。序号与 RFC id 的 `RNN` 后缀一致；删除 RFC 后不要求重新编号，也不复用已经发布的身份。

同一 feature 的 `docs/superplan/rfcs/F123.md` 与 `docs/superplan/rfcs/F123/` 互斥。发现两种布局同时存在时，全局校验失败并报告冲突路径。

### 3. 多 RFC 使用独立 id 和显式 feature 归属

目录内 RFC 使用以下 frontmatter：

```yaml
---
id: "F123-R01"
feature: "F123"
title: "存储模型"
status: "draft"
version: 1
source: "docs/superplan/human/features.md"
created: "YYYY-MM-DD"
---
```

`feature` 必须与父目录及现有 feature 请求完全一致。`id` 必须等于 `<feature>-R<NN>`，其中 `NN` 与文件名前缀一致。对于 branch-qualified feature，例如 `F123@storage-safe`，对应 id 为 `F123@storage-safe-R01`；显式 `feature` 字段消除分支后缀解析歧义。

RFC 使用 `RNN` 而不是 `NN`，避免与 `F123-01` 形式的 split plan id 混淆。RFC id 只标识设计文档；feature id 仍是请求生命周期和开发计划归属的唯一来源。

### 4. 两种布局共享正文、状态和版本规则

平铺和目录 RFC 都继续使用 `draft -> approved` 状态流、正整数审批版本以及 Git 修订历史。首次批准前修改不递增版本；approved RFC 的实质修改回到 `draft`、版本递增一次并重新审批。

多 RFC 的状态和版本彼此独立。修改其中一份 RFC 不改写其他 RFC 的版本，但 feature 的开发门禁会重新检查所有匹配 RFC，因此任何一份 RFC 回到 `draft` 都会阻止新计划通过全局校验。

### 5. Feature 级门禁要求所有匹配 RFC 获批

对于 `requires_rfc: true` 的 accepted feature：

- 尚无开发计划时，允许暂时没有 RFC、只有 draft RFC 或正在补充目录成员；
- 一旦存在任何非 `superseded` 开发计划，必须至少存在一份匹配 RFC；
- 平铺模式的唯一 RFC 必须为 `approved`；
- 目录模式的所有 RFC 都必须为 `approved`；
- feature 进入 `done` 时再次执行同样的全部批准检查。

首版不支持“部分 RFC 批准后先实施部分计划”。这保持现有 RFC 审批门的语义简单，也避免后加入 RFC 使已经开始的计划建立在不完整设计集合上。

### 6. Plan 引用精确路径并表达直接输入

平铺模式保持现有规则：每个非 `superseded` plan 必须在 `References` 中列出准确的平铺 RFC 路径。

目录模式下，每个非 `superseded` plan 必须引用至少一份属于同一 feature 的 RFC，且引用必须是 `docs/superplan/rfcs/<feature-id>/NN-<slug>.md` 的准确路径。Plan 不必引用与其交付边界无直接关系的其他 RFC；所有 RFC 的批准状态由 feature 级门禁统一保证。

校验器只接受 `References` 章节中的精确列表项，不从正文、标题或模糊文本推断依赖关系。

### 7. 发现器返回按 feature 分组的 RFC 集合

RFC 文档模型增加明确的 `feature_id`，使平铺 RFC 和目录 RFC 都可以通过统一接口参与校验。发现结果按 feature id 分组，而不是以 feature id 覆盖为单个文档。

发现和验证必须拒绝：

- `rfcs/` 下不符合平铺文件或一级 feature 目录的 Markdown；
- 更深层的子目录；
- 平铺文件与同名 feature 目录并存；
- 目录、`feature`、RFC id、文件序号不一致；
- 重复 RFC id 或重复序号；
- orphan、非 RFC-required 或 proposed feature 所属的 RFC；
- 不符合现有 source、status、version、created 契约的文档。

错误输出保持确定性，优先报告具体冲突路径和期望契约。

### 8. 指引保持精简并按需加载

`feature-plan-and-delivery` 继续只在显式 RFC 请求或 `requires_rfc: true` 时加载 RFC reference。`rfc-spec.md` 增加单 RFC 默认、多 RFC 使用条件、两种路径和独立 frontmatter 的最小说明；共享 plan spec 只保留跨产物引用与审批后果。

新 workspace 的 feature 指引和 README 同步说明双布局，但 migration 不改写已有用户维护的 human registry。行为场景覆盖单 RFC 兼容、多 RFC 选择、双布局冲突、全部审批门和直接引用，不增加独立 RFC catalog。

## 兼容性与迁移

- 所有现有 `docs/superplan/rfcs/<feature-id>.md` 保持有效。
- 现有 RFC frontmatter 不新增必填字段。
- 只有目录 RFC 需要新增 `feature` 字段和 `RNN` 身份。
- 现有计划对平铺 RFC 的准确引用保持有效。
- 初始化和 workspace migration 不移动或重写 RFC。
- 双布局属于向后兼容的插件能力扩展；除非实现验证发现生成 guardrail 契约必须改变，否则 workspace schema 保持 `1`。

## 已考虑的替代方案

### 所有 RFC 都强制使用目录

拒绝。它会增加普通单 RFC feature 的路径层级，并要求迁移已经有效的平铺文档，收益不足以覆盖兼容成本。

### 使用 `rfcs/F123/F123-1.md`

拒绝。父目录已经表达 feature id，重复前缀没有增加归属信息；`F123-01` 还容易与 split plan id 混淆。`01-<slug>.md` 配合 `F123-R01` 提供更清楚的路径和身份。

### 只在单个 RFC 内增加更多章节

保留为默认方案，但不足以表达真正独立的审批、版本和计划引用边界，因此不能覆盖全部需求。

### 每份 RFC 使用独立 feature

拒绝。设计主题仍共同交付一个用户价值和完成生命周期，拆分 feature 会使需求状态与实现归属失真。

### 允许 plan 在部分 RFC 批准后实施

拒绝首版采用。它需要 RFC 依赖关系、冻结集合、增量完成和变更失效语义，复杂度明显高于当前需求。

### 增加 RFC catalog 或索引文件

拒绝。当前 feature 查询、精确文件读取和全局校验足以支持预期规模；独立索引收益较低。

## 风险与缓解措施

- **身份歧义：** RFC id 可能与 split plan id 或 branch slug 混淆。通过显式 `feature` 字段、`RNN` 后缀和文件序号一致性校验缓解。
- **布局漂移：** 同一 feature 可能同时出现平铺与目录 RFC。通过互斥校验拒绝混合状态。
- **遗漏审批：** Plan 可能只引用一份 RFC 而遗漏其他 draft RFC。通过 feature 级全部批准门禁与 plan 级至少一个精确引用分别保证完整性和直接追踪。
- **过度拆分：** AI 可能为普通章节创建多份 RFC。通过“独立审批、版本或计划引用”条件约束，单 RFC 仍为默认。
- **兼容性回归：** 新模型可能错误要求旧 RFC 增加字段或移动路径。通过保留平铺解析分支和历史 fixture 回归覆盖。
- **错误失效范围：** 一份 RFC 回到 draft 会阻止整个 feature 的新计划。该行为与首版 feature 级门禁一致，并通过 RFC 指引明确说明。
- **文档与实现漂移：** 多个 guidance surface 可能描述不同路径。由 route-owned RFC spec 维护正文契约，共享 plan spec 只维护引用后果，测试锁定关键字符串与行为。

## 批准条件

当人类同意以下内容时，本 RFC 可以获批：

- 单 RFC 平铺路径保持默认并完全向后兼容。
- 多 RFC 使用 `rfcs/<feature-id>/NN-<slug>.md`，且与同名平铺文件互斥。
- 目录 RFC 使用 `<feature-id>-RNN` id、显式 `feature` 归属和匹配的文件序号。
- 所有匹配 RFC 获批后才能创建开发计划或完成 feature。
- 每个目录模式 plan 至少精确引用一份直接相关 RFC，不要求引用全部 RFC。
- 首版不支持部分批准实施、RFC 依赖图、独立 RFC catalog 或自动迁移。
- 现有平铺 RFC、计划引用、feature 生命周期和 workspace schema 保持兼容。
