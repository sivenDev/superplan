# Superplan Skill 路由与说明分层精简

## 摘要

精简 Superplan 的 agent-facing 流程说明，解决入口 skill、具体路由 skill、共享 reference 和人类模板之间的触发重叠与规则复述。保留现有四个根 skill 和条件 reference 架构，不新增独立 RFC skill，也不削弱 workspace safety、人工审批、状态完整性、bug 根因和交付验证边界。

本设计将 skill 限定为“触发、分发和路由特有差异”，将共享 reference 限定为单一规则权威；同时让低风险、单一交付边界的计划可以使用紧凑正文，避免自适应风险流程仍产生固定的仪式化计划。

## 背景与问题

当前总体架构已经具备合理分层：`using-superplan` 提供入口和共享资源，PRD、feature、bug 各有根 skill，RFC 与 debugging 只在对应路由中条件加载，脚本负责强制请求、RFC、计划和 workspace 不变量。

但长期增量演进使部分职责重新重叠：

- `using-superplan` 的 description 和 Route Entry 同时覆盖 project、feature、bug，而三个具体路由 skill 也直接匹配这些请求；自然语言请求可能产生重复选择或多加载一层入口说明。
- `using-superplan/SKILL.md` 已声明 `delivery-loop.md` 是共享生命周期权威，却又复述 workspace safety、compatibility、registry discovery、plan discovery 和 migration 处理。
- feature 与 bugfix skill 复述 `intake-spec.md`；feature skill 复述 `rfc-spec.md` 的判断和双审批；bugfix skill 复述 `debugging.md`、`plan-spec.md` 和 risk profile。
- `delivery-loop.md` 前半部分按主题定义 safety、checkpoint、risk 和 evidence，后半部分的完整 Delivery 列表再次展开同一规则。
- `plan-spec.md` 对所有风险级别要求同样的 `Architecture`、`Baseline` 和 `Change Map`。即使是边界明确的低风险说明修改，也容易生成与任务复杂度不成比例的计划正文和重复验证命令。
- 初始化后的 feature 模板承载了 RFC 路径、布局、语言和审批细节，超出了人类需求清单的最小职责。

这些问题不会立即破坏正确性，但会增加 agent 上下文、权威漂移和流程仪式化风险，也与仓库“skill 说明只增加微小说明、不要为了优化而优化”的规范不完全一致。

## 目标

- 保留四个根 skill，同时让自然语言 PRD、feature、bug 请求各有明确的首选路由。
- 让 `using-superplan` 专注初始化、检查、迁移和显式调用时的兜底分发。
- 让每个根 `SKILL.md` 只保留触发、输入、输出、条件 reference 加载点和路由特有差异。
- 让每条行为规则只有一个 agent-facing 权威来源，其他层级只保留必要引用或跨产物后果。
- 将 `delivery-loop.md` 保持为共享生命周期权威，但消除主题规则与完整 Delivery 复述之间的重复。
- 为低风险、单一交付边界工作提供紧凑 plan 契约，同时保持中高风险计划的完整表达能力。
- 避免 focused、final 和 metadata-only 验证之间重复执行已被权威命令包含的检查。
- 保留现有审批、安全、状态、追踪和兼容性保证，并通过行为场景验证语义没有丢失。

## 非目标

- 不合并四个根 skill，也不新增第五个根 skill。
- 不把 RFC、debugging、worktree 或 verification 提升为独立顶层路由。
- 不删除 workspace safety、checkpoint commit、RFC 审批、plan 审批或最终交付 commit。
- 不改变 human、RFC 或 plan 的编号和状态值。
- 不改变 branch-qualified request id、split plan、multi-RFC 或完成边界。
- 不削弱 accepted bug 的复现、根因和行为级回归要求。
- 不以行数或 token 数作为独立验收目标；只有能消除重复权威、触发歧义或实际流程负担的精简才实施。
- 不在本设计中修改 workspace schema、发布插件版本、推送远端或刷新本地安装。
- 不重写已完成的历史请求、RFC 或计划正文。

## 决策

### 1. 保留四个根 skill，但划分自然语言触发职责

四个根 skill 继续存在：

- `using-superplan`：初始化、检查、迁移；当人类明确调用 `$using-superplan` 或请求只表达“使用 Superplan”而尚未确定类型时，负责兜底分发。
- `project-bootstrap-from-prd`：从 `docs/superplan/human/prd.md` 开始的首次项目规划。
- `feature-plan-and-delivery`：新建或继续 feature。
- `bugfix-plan-and-delivery`：新建、诊断或继续 bug。

`using-superplan` 不再把 project、feature、bug 的完整交付行为写入自身 Route Entry。它只确认 workspace 入口语义并把请求交给具体路由。具体路由仍直接读取共享 `delivery-loop.md`，因此自然语言请求不需要先加载入口 skill 才能安全执行。

插件和 skill metadata 必须继续允许人类显式使用 `$using-superplan` 作为总入口，但自然语言描述应避免让总入口与具体路由看起来具有同等首选权。

### 2. 为 agent-facing 规则建立唯一权威

规则归属固定为：

| 产物 | 唯一职责 |
| --- | --- |
| 根 `SKILL.md` | 触发边界、输入输出、需要加载的共享或局部 reference、路由特有差异 |
| `delivery-loop.md` | 跨路由 lifecycle、workspace safety、checkpoint、risk、evidence、approval、completion 和 delivery |
| `intake-spec.md` | 新 feature/bug 的记录、direct acceptance 和 request review pause |
| `plan-spec.md` | plan metadata、正文契约、状态字段、依赖和 plan-set validation |
| `verification-matrix.md` | changed artifact 到 focused/final verification 的映射 |
| `worktrees.md` | 人类接受隔离后的 worktree 执行细节 |
| `rfc-spec.md` | feature RFC 的选择、文档、版本和审批规则 |
| `debugging.md` | accepted bug 在规划前的诊断和根因规则 |
| human assets | 面向人类的最小录入格式和状态含义 |
| README / install docs | 面向安装者和维护者的说明，不作为 agent workflow 权威 |

根 skill 可以说明“何时读取”某一 reference，但不复述 reference 内的判断步骤、命令序列和审批后果。共享 reference 可以说明跨产物约束，但不得复制局部 reference 的完整正文契约。

### 3. `using-superplan` 和三个路由 skill 采用最小正文

`using-superplan/SKILL.md` 保留：

- `delivery-loop.md` 的权威声明；
- 初始化、检查和迁移入口；
- 显式 `--root` 行为和 workspace-only 边界；
- 三条路由映射。

现有 Route Entry 五步由一句“对 routed work 应用 delivery loop，然后分发至对应 route skill”替代。

三个具体路由 skill 保留各自 Input、Output、Plan type 和条件 reference：

- feature skill 只说明新请求读取 intake、RFC 候选或显式选择读取 RFC spec、计划遵循 plan spec；RFC 累计判断和双审批不再在 skill 中展开。
- bugfix skill 只说明新请求读取 intake、根因未证实时读取 debugging、计划遵循 plan spec；复现与回归细节不再重复。
- project bootstrap 只说明 PRD 来源、mainline plan 类型以及 PRD 不被计划替代；不复述 workspace check 和 migration 规则。

### 4. `delivery-loop.md` 保留主题权威，Delivery 改为短状态机

`delivery-loop.md` 继续集中跨路由规则，避免拆成大量容易漏读的小 reference。Workspace Safety、Human-Decision Checkpoints、Risk Profiles 和 Evidence and Verification 保持独立章节。

现有十步 Delivery 不再逐项重述这些章节，而改为六阶段状态机：

1. Safety and compatibility
2. Intake or diagnosis
3. Draft and approval
4. Implementation
5. Verification and progress completion
6. Commit and optional worktree handoff

每个阶段只说明状态转换和引用的权威章节。兼容性异常处理仍保留，但只在 compatibility check 非 current 时应用；正常路径不反复解释历史 recovery 情形。

### 5. Plan 正文根据风险和信息量选择紧凑或完整形式

所有 plan 继续要求稳定 frontmatter、`Goal`、`Scope`、`Non-Goals`、`Exit Criteria`，以及至少一个包含 `Outcome`、`Files`、`Verification` 和结果 checkbox 的任务。

以下字段改为条件必需：

- `Architecture`：存在边界、契约、设计方向或不可从 Scope 直接得出的实现约束时必需。
- `Baseline`：存在影响执行的当前事实、已知失败、迁移起点或兼容条件时必需。
- `Change Map`：多文件、多符号或策略边界需要说明职责分配时必需；单一机械边界可以省略。

中高风险、跨模块、迁移、公共契约和复杂 bug 默认继续使用完整形式。Bugfix 仍必须包含 `Reproduction` 和 `Root Cause`。紧凑形式不允许省略非目标、可观察退出条件、文件范围或验证证据。

历史计划不因缺少或包含任何条件字段而失效；该决策只改变新计划的 agent-facing 编写契约。

### 6. 验证说明区分 iteration、final 和 metadata-only 阶段

`verification-matrix.md` 继续选择 changed artifact 对应的验证，但明确：

- focused checks 用于实现迭代，可以被最终完整回归再次覆盖；
- final evidence 对稳定实现只运行一次权威完整命令；
- 如果 `tools/verify_repo.py` 已包含 registry、guardrail、plan-index、编译、测试或 diff check，计划不得把这些命令再次描述为独立 final 检查；
- 完成后的 metadata-only 更新只运行受影响的 registry、plan index 和 status/diff 检查，不重跑实现回归；
- `git status` 属于归属检查，可以在最终提交边界保留，不视为代码回归。

计划的 Verification 应表达需要证明的声明和实际入口命令，不为显得完整而枚举同一命令内部已经执行的子检查。

### 7. Human 模板保持人类录入粒度

Feature 模板继续说明 id、status、direct acceptance、简短正文和可选 `requires_rfc: true`，但不再展开单/多 RFC 路径、默认语言、编号和全部审批规则。模板只说明：需要 RFC 的 feature 在规划前必须完成独立设计审批，具体格式由 Superplan RFC 流程管理。

README 可以保留面向维护者的 RFC、workspace 和 adaptive workflow 概览，但必须明确以 skill/reference 和脚本校验为权威。README 的重复不进入 agent 的正常路由上下文，因此不以同样标准机械删减。

### 8. 保留所有安全和状态不变量

本次精简不得改变：

- intake 默认 `proposed`，只有显式、忠实、无实质歧义时直接 `accepted`；
- RFC draft 和 plan draft 分别需要人工批准；
- 不从 `draft` 实施；
- workspace safety 在有覆盖、混入或冲突风险时先询问 worktree；
- 人类决策暂停前只 checkpoint 当前任务的有效变更；
- bugfix 先建立可信根因并保留行为级回归；
- feature/bug 只有在所有非 superseded 相关计划 complete 后才能 done；
- task-level commit 与 checkpoint commit 分离；
- linked worktree 的 merge 和 cleanup 分别授权；
- 证据只在相关状态未变化时复用。

## 兼容性与迁移

- 四个根 skill 名称和目录保持不变。
- CLI 路径、参数、human/RFC/plan frontmatter、状态和编号保持不变。
- workspace schema 保持 `1`；初始化和 migration 不需要改写已有用户维护的 human 文件。
- 现有完整格式 plan 保持有效，不迁移历史 plan。
- 紧凑 plan 只放宽 agent-facing 正文要求，不改变生成器已经强制的 metadata 和跨产物不变量。
- Skill metadata、README 和行为测试需要同步触发与职责变化，但插件安装方式保持不变。
- 如果实施发现某项“说明精简”需要改变脚本公共行为、历史产物有效性或 workspace schema，必须返回 RFC 重新评审，而不能在开发计划中静默扩大范围。

## 已考虑的重要替代方案

### 合并为一个根 skill

拒绝。它会让所有任务加载 project、feature、bug、RFC 和 debugging 说明，降低触发精度并破坏当前条件引用边界。

### 保留当前正文，只依赖高能力模型忽略重复

拒绝。重复权威不仅消耗上下文，还会在后续修改只更新其中一处时形成行为漂移；这是职责问题，不只是 token 优化。

### 把 delivery loop 拆成大量更小 reference

拒绝作为本次默认方案。过多条件文件会增加漏读和路由复杂度。当前主要问题是同一文件内部复述，以及根 skill 复述 reference，而不是 delivery loop 缺少文件拆分。

### 删除计划审批或 checkpoint commit 来缩短流程

拒绝。它们分别承担实施授权和跨回合安全交接，不属于说明重复。

### 所有 plan 都使用极简模板

拒绝。中高风险、公共契约、迁移和复杂 bug 仍需要完整 Architecture、Baseline 和 Change Map。紧凑形式只适用于这些字段没有新增决策价值的任务。

### 只删 README 的重复说明

拒绝作为主要方案。README 面向人类且不在正常 agent route 中加载；真正的成本和漂移位于根 skill 与 runtime reference 之间。

## 风险与缓解措施

- **触发覆盖下降：** 收窄 `using-superplan` 后，模糊请求可能未进入具体路由。通过保留显式总入口、准确的三个路由 description、UI prompt 和 fresh-context trigger 场景缓解。
- **过度压缩导致规则丢失：** 删除复述时可能误删唯一约束。实施前建立规则归属清单，修改后检查四个根 skill 和所有直接 reference，并运行受影响行为场景。
- **紧凑 plan 信息不足：** Agent 可能错误省略重要 Architecture 或 Baseline。通过条件必需定义、高风险默认完整格式、Exit Criteria 和 Verification 不可省略来限制。
- **验证被错误跳过：** 去重可能被理解为减少最终证据。明确只移除已被权威命令覆盖的重复执行，仍按 artifact 和 risk 选择 final evidence。
- **Human 模板过度简化：** 用户可能不知道 RFC 基本含义。保留 `requires_rfc`、独立设计审批和 AI 入口说明，详细格式由运行时 skill 与 README 提供。
- **文档与 metadata 漂移：** Skill description、UI prompt、README 和行为场景可能不同步。通过 package contract、四 skill 检查和 applicable fresh-context scenarios 验证。
- **历史计划被误判：** 放宽新计划格式时可能影响旧计划。明确不增加正文解析校验，不迁移历史文件，并用现有计划索引和全量仓库验证证明兼容。

## 可观察的批准条件

当人类同意以下内容时，本 RFC 可以获批：

- 保留四个根 skill，不新增或合并顶层路由。
- `using-superplan` 专注 setup/check/migrate 和显式兜底分发，PRD、feature、bug 自然语言请求由具体路由优先处理。
- 根 skill 只保留触发、输入输出、条件 reference 和路由差异；共享或局部规则只有一个权威来源。
- `delivery-loop.md` 保持共享权威，但用短状态机替代重复的十步规则复述。
- 低风险单边界任务可以省略没有决策价值的 Architecture、Baseline 和 Change Map；核心范围、非目标、退出条件、文件和验证仍必需。
- 最终验证不重复执行权威命令已经包含的子检查，metadata-only 更新继续使用局部验证。
- Human feature 模板不再承载 RFC 布局、语言和编号细节。
- 所有 workspace safety、审批、checkpoint、bug 根因、完成状态和 Git 追踪边界保持不变。
- 不改变 CLI、状态、编号、历史产物有效性、workspace schema、发布或安装状态。
